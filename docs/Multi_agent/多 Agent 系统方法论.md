# Coding Agent Harness 多 Agent 系统最终方法论

## 一、核心结论

面向软件工程任务，当前最可靠的多 Agent Harness 不是“多个角色自由聊天”，也不是尽可能扩大 Agent 数量，而是：

> **以单 Agent 为默认执行单元，由中心调度器选择性地调用专业 Agent；通过任务契约和依赖图组织工作；读取任务并行，写入任务使用独立工作树或容器隔离；Agent 之间通过版本化工件交接；最终由确定性测试、独立评审和人类审批完成收口。**

当前主流做法可以概括为：

**中心化编排 + 专业化分工 + 显式任务状态 + 隔离写入 + 串行合并 + 确定性质量门禁。**

代表先进方向的做法是：

- 将编排逻辑写成可执行工作流、DAG 或状态机；
    
- 根据预期收益动态决定是否启动子 Agent；
    
- 用任务账本、提交、测试记录和事件日志代替共享聊天记忆；
    
- 将执行权限、策略审核和人类审批分离；
    
- 基于历史任务自动优化模型、角色、拓扑和调度策略；
    
- 支持长任务检查点、局部重算和 Harness 自进化。
    

但其中只有选择性委派、工作树隔离、持久状态和确定性门禁已有较强实践验证。自动团队组建、共享长期记忆、信用分配和 Harness 自修改仍主要属于研究方向。

# 二、统一设计原则：最小化协调面

多 Agent 系统的收益来自并行和专业化，损失来自协调、上下文交接、重复检索、代码冲突和额外验证。

因此，多 Agent Harness 的核心目标不是最大化 Agent 数，而是：

> **在获得必要并行收益的同时，最小化 Agent 之间需要共享、同步和协商的状态。**

可以用以下关系理解是否值得拆分：

[  
多Agent净收益 =  
质量增益

- 关键路径缩短
    

- 调度成本
    
- 上下文损失
    
- 代码冲突风险
    
- 额外验证成本  
    ]
    

只有预期净收益为正时，才应使用多 Agent。

整个方法论建立在八项原则上。

## 原则一：单 Agent 优先

任何任务首先由一个具备完整工具能力的 Agent 尝试完成。

只有出现以下情况时才增加 Agent：

- 存在两个以上相互独立的工作单元；
    
- 单 Agent 上下文正在被大量搜索结果或日志污染；
    
- 不同子任务需要明显不同的工具、模型或权限；
    
- 多个候选方案可以通过测试可靠比较；
    
- 任务可以通过工作流重复执行；
    
- 并行收益明显高于协调和验证成本。
    

多 Agent 必须与强单 Agent 基线比较，不能因为系统支持并发就默认开启并发。

---

## 原则二：先定义任务契约，再启动 Agent

每个任务必须先被转换成显式执行契约，包括：

|字段|内容|
|---|---|
|目标|要解决的问题和期望结果|
|非目标|明确不处理的内容|
|基线|仓库、分支、提交和环境版本|
|输入|文件、日志、接口、前序工件|
|写入范围|允许修改的目录、文件或模块|
|输出|补丁、提交、报告、测试或结构化数据|
|验收条件|编译、测试、性能、安全或业务条件|
|权限|文件、命令、网络、凭据和外部系统权限|
|预算|时间、Token、调用次数和并发额度|
|终止条件|成功、无进展、资源耗尽或人工取消|

没有验收条件的任务不适合自动分解，因为系统无法判断子 Agent 是否真正完成。

---

## 原则三：并发读取，隔离写入，串行合并

这是 Coding Agent Harness 最重要的工程约束。

### 读取任务

代码搜索、依赖分析、测试定位、日志分析和文档检索可以基于同一不可变仓库快照并行执行。

### 写入任务

每个写入 Agent 必须拥有：

- 独立容器或虚拟机；
    
- 独立 Git worktree；
    
- 独立分支；
    
- 明确的文件或模块所有权；
    
- 独立测试结果；
    
- 可回滚提交。
    

不应让多个写入 Agent 同时修改一个共享工作目录。

### 合并任务

只有一个 Merge Coordinator 可以更新集成分支。

合并遵循：

1. 按依赖图顺序合并；
    
2. 每次合并后运行增量测试；
    
3. 全部合并后运行集成和回归测试；
    
4. 冲突不得静默覆盖；
    
5. 冲突应转换成新的显式修复任务；
    
6. 多个候选补丁默认选一个，不自动拼接。
    

可将规则记为：

> **一个任务、一个所有者、一个分支、一套验收条件、一条审计链。**

---

## 原则四：工件是事实源，聊天只是临时界面

Agent 之间不应依靠自由聊天维持系统状态。

推荐使用以下权威工件：

|信息类型|权威载体|
|---|---|
|任务进度|任务账本或状态数据库|
|任务依赖|DAG|
|代码状态|Git 提交和分支|
|设计决策|版本化设计工件|
|验证结果|测试、构建和扫描报告|
|权限记录|工具调用和审批日志|
|恢复状态|事件日志和检查点|
|长期经验|带来源和版本的仓库记忆|

Agent 返回结果时，应提交结构化交接工件，而不是只发送“已经完成”或自然语言摘要。

推荐的交接格式包括：

- 完成了什么；
    
- 修改了哪些文件；
    
- 关键设计决策；
    
- 执行了哪些测试；
    
- 哪些测试未执行；
    
- 已知风险；
    
- 依赖的前提；
    
- 后续任务建议；
    
- 对应提交哈希。
    

---

## 原则五：调度器负责控制，Agent 负责解决问题

调度器不应依赖模型上下文临时记住整个工作流。

调度器应确定性地管理：

- 任务状态；
    
- 依赖关系；
    
- Agent 所有权；
    
- 并发额度；
    
- 预算；
    
- 超时；
    
- 重试；
    
- 权限；
    
- 检查点；
    
- 终止条件。
    

Agent 负责：

- 理解局部任务；
    
- 使用工具获取证据；
    
- 生成代码或分析结果；
    
- 根据测试反馈修复；
    
- 提交结构化工件。
    

这种职责分离可以避免模型遗忘任务状态、重复启动任务或绕过系统约束。

---

## 原则六：权限由基础设施控制，而不是由提示词控制

“不要访问网络”“不要修改生产环境”不能只写在提示词里。

Harness 必须通过确定性系统实施：

- 容器或操作系统沙箱；
    
- 默认拒绝网络；
    
- 网络域名允许列表；
    
- 文件路径允许和拒绝规则；
    
- 最小权限令牌；
    
- 临时凭据；
    
- 命令策略；
    
- 审批工作流；
    
- 工具调用审计。
    

建议采用分级权限：

|风险等级|操作|默认策略|
|---|---|---|
|R0|搜索、读取、运行已有测试|自动允许|
|R1|修改独立工作树、创建测试|自动允许并记录|
|R2|安装依赖、访问允许列表网络|策略审核或一次性批准|
|R3|推送分支、创建 PR、修改外部系统|人类或组织策略批准|
|R4|生产、密钥、权限、支付、数据库迁移|强制人类审批|

可以使用独立策略 Agent 辅助评审权限请求，但策略 Agent只能缩小权限，不能创造系统原本没有的权限。

---

## 原则七：确定性验证优先于 Agent 共识

“另一个 Agent 认为代码正确”不是可靠的质量证明。

质量证据的优先级应为：

1. 可复现问题；
    
2. 编译结果；
    
3. 静态检查和类型检查；
    
4. 针对性测试；
    
5. 集成和回归测试；
    
6. 安全和依赖扫描；
    
7. 独立代码评审；
    
8. 人类验收；
    
9. 线上运行结果。
    

LLM reviewer 适合发现：

- 漏掉的边界条件；
    
- 可维护性问题；
    
- 安全风险；
    
- 需求与实现不一致；
    
- 测试覆盖不足。
    

但 reviewer 不能替代编译、测试和安全策略。

---

## 原则八：以被接受的软件变更衡量系统

不应使用以下指标衡量多 Agent 系统：

- Agent 数量；
    
- 对话轮数；
    
- 生成代码量；
    
- 子任务完成数量；
    
- 自我报告的成功率。
    

核心指标应是：

> **每个被接受且未回滚的软件变更所需的总成本、关键路径时间、人工评审时间和风险。**

建议持续记录：

|指标类别|核心指标|
|---|---|
|质量|接受率、测试通过率、回归率、回滚率|
|效率|p50/p95 时延、关键路径时间、人工评审时间|
|成本|每个成功任务的 Token、模型、容器和构建成本|
|协作|委派成功率、交接失败率、合并冲突率|
|工具|工具失败率、权限拒绝率、重复调用率|
|恢复|检查点恢复率、局部重算率、重复失败率|
|安全|越权请求、安全门禁失败和人工拦截次数|

# 三、推荐的五种系统设计范式

## 范式一：监督者与专业子 Agent

### 工作原理

一个主 Agent 持有全局目标，把代码搜索、测试分析、日志分析、文档检索或代码评审委派给专业子 Agent。

子 Agent 使用独立上下文，只返回结构化结论和证据。

### 适用场景

- 大型仓库探索；
    
- 多来源信息检索；
    
- 日志和错误分析；
    
- 测试设计；
    
- 独立代码评审；
    
- 主 Agent 上下文压力较大。
    

### 优势

- 减少主上下文污染；
    
- 读取任务容易并发；
    
- 可以为不同角色使用不同工具和模型；
    
- 权限边界容易控制。
    

### 局限

- 交接摘要可能损失细节；
    
- 主 Agent 仍是信息汇总瓶颈；
    
- 过度拆分会增加成本；
    
- 不适合多个 Agent 共同频繁修改同一模块。
    

### 推荐定位

这是从单 Agent 进入多 Agent 的第一步，应优先增加只读子 Agent，而不是并行写入 Agent。

---

## 范式二：任务 DAG 与共享任务账本

### 工作原理

将目标分解为带依赖关系的任务节点。

每个节点至少包含：

- 状态；
    
- 依赖；
    
- 所有者；
    
- 输入；
    
- 输出；
    
- 写入范围；
    
- 验收条件；
    
- 预算；
    
- 重试次数。
    

调度器只启动依赖已满足的节点。

### 适用场景

- 多阶段任务；
    
- 大型迁移；
    
- 多模块重构；
    
- 长时间运行；
    
- 需要断点恢复和审计的任务。
    

### 优势

- 进度和阻塞可观察；
    
- 可以局部重试；
    
- 可以执行关键路径调度；
    
- 支持缓存和局部重算；
    
- 比自由聊天更容易控制终止。
    

### 局限

- 初始错误分解会固化成错误计划；
    
- 隐性依赖可能在执行后才被发现；
    
- 紧耦合代码会导致频繁重构 DAG；
    
- 对小任务不划算。
    

### 推荐定位

任务图必须允许动态修改，但修改应由调度器记录，而不是由 Agent 在聊天中隐式改变。

---

## 范式三：Worktree 分片并行

### 工作原理

多个写入 Agent 从同一基线提交创建独立 worktree 和分支，各自修改不重叠的模块，完成后由统一集成者合并。

### 适用场景

- 不同模块的独立修改；
    
- 多语言绑定同步更新；
    
- 多个独立测试文件；
    
- 机械式 API 迁移；
    
- 文档和代码并行修改；
    
- 大批量低耦合变更。
    

### 优势

- 避免工作区相互覆盖；
    
- 支持独立回滚和重试；
    
- 与 Git 和 PR 流程兼容；
    
- 每个 Agent 的产出可独立审查。
    

### 局限

- 无法消除语义冲突；
    
- 跨模块接口修改仍需要协调；
    
- 多环境构建成本较高；
    
- 合并和集成测试可能成为瓶颈。
    

### 推荐定位

写入并发数应由独立代码所有权数量决定，而不是由平台最大并发能力决定。

生产初期建议只允许 2 至 4 个并行写入 Agent。

---

## 范式四：候选生成与独立验证

### 工作原理

多个 Agent 分别生成候选补丁，然后通过测试、静态分析、性能结果或独立 reviewer 选择一个候选。

### 适用场景

- 解法不确定性高；
    
- 存在多个合理实现；
    
- 候选可以被确定性测试区分；
    
- 错误结果代价较高；
    
- 候选生成成本低于错误修复成本。
    

### 优势

- 提高方案多样性；
    
- 将生成和裁决分离；
    
- 可以缓解单一路径推理失败；
    
- 适用于算法、性能和复杂缺陷修复。
    

### 局限

- 成本随候选数量增加；
    
- reviewer 可能与生成者产生相关错误；
    
- 没有可靠测试时难以选择；
    
- 多候选不一定比单候选更好。
    

### 推荐定位

默认选择一个完整候选，不自动拼接多个候选的局部代码。

---

## 范式五：Workflow-as-Code

### 工作原理

用 Python、JavaScript、YAML、DAG 或状态机表达编排过程。

工作流代码负责：

- 生成任务；
    
- 创建 Agent；
    
- 保存状态；
    
- 控制并发；
    
- 处理失败；
    
- 执行重试；
    
- 判断终止；
    
- 收集结果；
    
- 触发门禁。
    

### 适用场景

- 大规模依赖升级；
    
- 批量安全审计；
    
- 测试生成；
    
- 重复性迁移；
    
- 跨多个仓库的规则化修改；
    
- 数小时或数日的长任务。
    

### 优势

- 流程可重放；
    
- 状态可检查；
    
- 工作流可以代码评审；
    
- 支持缓存和局部重算；
    
- 不依赖模型记住全部状态。
    

### 局限

- 工作流本身需要开发和维护；
    
- 高度开放的问题难以预先编码；
    
- 错误工作流可能大规模复制错误；
    
- 工作流版本变化也需要回归测试。
    

### 推荐定位

重复执行三次以上、流程已经相对稳定的任务，才值得固化为 Workflow-as-Code。

## 4.2 核心组件

### Contract Compiler

把需求转换成执行契约，输出：

- 目标和非目标；
    
- 修改范围；
    
- 基线版本；
    
- 验收条件；
    
- 权限和风险；
    
- 预算和终止规则。
    

### Repository Intelligence

提供：

- 代码搜索；
    
- 符号和调用关系；
    
- 构建与测试映射；
    
- 模块所有权；
    
- 历史提交；
    
- 依赖关系；
    
- 代码索引。
    

它只提供证据，不直接决定代码修改。

### Planner

将任务拆成 DAG，并为每个节点确定：

- 输入；
    
- 输出；
    
- 依赖；
    
- 写入范围；
    
- 验收方式；
    
- 预估成本；
    
- 冲突风险。
    

### Scheduler

决定：

- 保持单 Agent；
    
- 启动只读子 Agent；
    
- 启动并行 writer；
    
- 使用候选竞争；
    
- 使用何种模型；
    
- 何时暂停、重试或终止。
    

### Workspace Manager

负责：

- 固定基线提交；
    
- 创建容器和 worktree；
    
- 分配分支；
    
- 管理文件所有权；
    
- 缓存依赖和构建；
    
- 清理失效环境。
    

### Tool Gateway

所有工具调用必须经过统一网关。

网关负责：

- 权限校验；
    
- 参数过滤；
    
- 网络控制；
    
- 凭据注入；
    
- 超时；
    
- 审批；
    
- 幂等；
    
- 审计。
    

### Durable State Store

保存：

- DAG；
    
- 任务状态；
    
- Agent 状态；
    
- 事件日志；
    
- 工具结果；
    
- 检查点；
    
- 提交和测试工件；
    
- 预算消耗；
    
- 失败原因。
    

### Quality Plane

包含：

- 编译；
    
- lint；
    
- 类型检查；
    
- 单元测试；
    
- 集成测试；
    
- 回归测试；
    
- 安全扫描；
    
- 独立 reviewer；
    
- 差异范围检查。
    

### Merge Coordinator

负责：

- 验证提交来源；
    
- 按 DAG 顺序合并；
    
- 检查文件所有权；
    
- 处理冲突；
    
- 触发集成测试；
    
- 将失败转换成新任务。
    

### Observability Controller

记录：

- 每个任务的状态变化；
    
- 模型和提示版本；
    
- 工具调用；
    
- Token、成本和时延；
    
- 权限请求；
    
- 分支和提交；
    
- 测试和门禁结果；
    
- 人工介入；
    
- 最终接受或回滚结果。

# 五、标准关键数据流

## 步骤一：冻结输入

记录：

- 原始需求版本；
    
- 仓库基线 commit；
    
- 依赖锁文件；
    
- 构建环境；
    
- 可用测试；
    
- 权限范围。
    

后续需求或基线发生变化时，相关节点必须标记为过期。

## 步骤二：形成执行契约

将自然语言请求转换为机器可检查的目标、范围、验收和预算。

## 步骤三：只读侦察

并行启动有限数量的只读 Agent，分析：

- 失败位置；
    
- 调用链；
    
- 相关测试；
    
- 影响范围；
    
- 潜在修改点；
    
- 模块依赖。
    

## 步骤四：构建任务图

根据侦察结果生成 DAG。

尽量让写入任务对应独立模块或独立文件集合。

## 步骤五：选择执行拓扑

调度器根据任务特征选择：

|任务特征|推荐拓扑|
|---|---|
|小型、紧耦合|单 Agent|
|搜索范围大、写入集中|Supervisor + 只读子 Agent|
|多模块、低重叠|DAG + 独立 worktree|
|解法不确定、测试充分|best-of-N|
|大规模重复流程|Workflow-as-Code|
|高风险操作|Agent + 独立评审 + 人类审批|

## 步骤六：隔离执行

写入 Agent 获得：

- 固定基线；
    
- 独立 worktree；
    
- 路径所有权；
    
- 最小权限；
    
- 节点级验收条件。
    

## 步骤七：节点级验证

每个节点至少完成：

- 修改范围检查；
    
- 编译或静态检查；
    
- 针对性测试；
    
- 结构化交接；
    
- Git 提交。
    

## 步骤八：串行集成

Merge Coordinator 按依赖顺序合并。

发生冲突时，不让原 Agent 在未知集成状态下直接继续，而是生成新的冲突解决任务。

## 步骤九：全局质量门禁

运行：

- 全量构建；
    
- 集成测试；
    
- 回归测试；
    
- 安全扫描；
    
- 独立代码评审。
    

## 步骤十：审批和学习

高风险变更交由人类审批。

只有最终被接受且未回滚的结果，才能进入长期仓库记忆或可复用 Skills。

---

# 六、选择性委派规则

调度器默认不委派。

满足以下条件时，适合启动只读子 Agent：

- 搜索空间大；
    
- 信息来源相互独立；
    
- 输出可以结构化；
    
- 主 Agent 上下文压力大；
    
- 不涉及共享写入。
    

满足以下条件时，适合启动并行 writer：

- 修改文件集合基本不重叠；
    
- 模块接口稳定；
    
- 子任务可以独立测试；
    
- 有清楚的合并顺序；
    
- 并行节省明显超过环境和合并成本。
    

满足以下任一条件时，应保持单 Agent：

- 修改集中在同一核心文件；
    
- 需求仍在快速变化；
    
- 子任务需要频繁互相协商；
    
- 没有自动化验收；
    
- 构建环境难以复制；
    
- 一个架构决策会影响全部实现；
    
- 任务本身很小。
    

满足以下条件时，适合候选竞争：

- 多种解法均合理；
    
- 结果可以通过测试、性能或安全指标比较；
    
- 错误解法成本较高；
    
- 生成多个候选的成本可接受。
    

---

# 七、状态、记忆与通信模型

## L0：Agent 临时上下文

包含当前任务的推理、最近工具结果和短期计划。

特点：

- 可以压缩；
    
- 可以丢弃；
    
- 不作为系统事实源；
    
- 不直接用于长任务恢复。
    

## L1：任务级权威状态

包含：

- 任务 DAG；
    
- 节点状态；
    
- 基线提交；
    
- 工作树和分支；
    
- 工具调用；
    
- 测试结果；
    
- 检查点；
    
- 审批记录；
    
- 预算和终止原因。
    

这是审计和恢复的事实源。

## L2：长期仓库记忆

包含：

- 架构和模块知识；
    
- 构建与测试方法；
    
- 已验证调试步骤；
    
- 组织规范；
    
- 常见失败模式；
    
- 可复用工作流。
    

每条长期记忆必须带有：

- 来源任务；
    
- 仓库和版本；
    
- 创建时间；
    
- 验证状态；
    
- 维护者；
    
- 适用范围；
    
- 过期条件；
    
- 回滚记录。
    

未通过最终质量门禁的经验不得写入长期记忆。

# 八、失败恢复和终止策略

## 失败分类

|失败类型|处理方式|
|---|---|
|临时网络或工具失败|使用幂等键和退避重试|
|编译或测试失败产生新证据|将失败工件返回原 Agent，允许继续|
|重复同类失败|更换策略、模型或任务分解|
|权限拒绝|停止循环请求，升级人工或终止|
|合并冲突|交由 Merge Coordinator，生成修复节点|
|上游输入变化|标记下游过期，只重跑受影响节点|
|预算耗尽|保存检查点，明确终止|
|环境不可复现|转人工处理，不伪装成功|

## 无进展判断

满足以下情况可判定无进展：

- 连续多轮没有新增代码变化；
    
- 没有新增测试或诊断证据；
    
- 同一工具调用重复失败；
    
- 测试结果没有改善；
    
- Agent 重复相同计划；
    
- 已达到预算或重试上限。
    

初始系统可以采用：

- 同类错误最多自动重试两次；
    
- 允许一次更换策略或模型；
    
- 再次失败后转人工或终止。
    

具体阈值应根据内部任务数据校准。

## 成功终止

只有同时满足以下条件才标记成功：

- 执行契约中的验收条件全部满足；
    
- 修改范围合法；
    
- 节点测试通过；
    
- 集成和回归门禁通过；
    
- 必要审批完成；
    
- 代码已经进入指定提交、分支或 PR。
    

Agent 自我声明“完成”不构成成功条件。

# 九、质量门禁体系

|门禁|检查内容|裁决主体|
|---|---|---|
|G0 问题门禁|问题可复现，需求、范围和基线明确|脚本 + 人类契约|
|G1 静态门禁|格式、lint、类型、编译|确定性工具|
|G2 节点测试|与本次修改直接相关的测试|确定性工具|
|G3 约束门禁|修改路径、API、不变量、依赖变化|规则 + reviewer|
|G4 独立评审|逻辑、边界、安全、可维护性|独立 Agent|
|G5 集成门禁|全量回归、跨模块测试、安全扫描|确定性工具|
|G6 风险审批|生产、认证、支付、数据迁移|人类|

核心规则：

> **Agent reviewer 可以补充确定性门禁，但不能替代确定性门禁。**

# 十、实施路线

## 阶段 0：强单 Agent

实现：

- 仓库搜索；
    
- Shell；
    
- 编辑；
    
- 测试；
    
- 沙箱；
    
- 基本日志；
    
- 成本和超时控制。
    

目标是建立真实基线，并能区分：

- 模型失败；
    
- 工具失败；
    
- 环境失败；
    
- Harness 失败。
    

没有这一阶段，不应讨论多 Agent 带来的收益。

---

## 阶段 1：只读专业 Agent

首先增加：

- Repository Scout；
    
- Test Analyst；
    
- Failure Analyst；
    
- Documentation Researcher；
    
- Code Reviewer。
    

这些 Agent 默认没有代码写权限。

目标是验证：

- 是否减少主 Agent 上下文消耗；
    
- 是否降低搜索失败；
    
- 是否减少无效工具调用；
    
- 是否缩短问题定位时间。
    

---

## 阶段 2：独立 worktree 写入

只允许边界清楚的任务并行写入。

增加：

- Workspace Manager；
    
- 路径所有权；
    
- 独立分支；
    
- 节点级测试；
    
- 结构化交接；
    
- 单一 Merge Coordinator。
    

目标是验证：

- 并行是否缩短关键路径；
    
- 合并冲突是否可控；
    
- 集成失败是否低于收益。
    

---

## 阶段 3：任务 DAG 和持久状态

增加：

- 任务账本；
    
- 依赖关系；
    
- 事件日志；
    
- 检查点；
    
- 幂等工具调用；
    
- 局部重算；
    
- 明确终止状态。
    

完成这一阶段后，系统才具备处理长任务的基本能力。

---

## 阶段 4：选择性委派和模型路由

根据历史数据决定：

- 哪些任务保持单 Agent；
    
- 哪些任务启动只读 Agent；
    
- 哪些任务值得并行写入；
    
- 哪些节点使用强模型；
    
- 哪些节点使用低成本模型；
    
- 哪些任务需要 reviewer；
    
- 哪些操作必须人工审批。
    

初期使用可解释规则，不应立即使用黑盒学习调度器。

---

## 阶段 5：自适应与自进化

在前四阶段已具有可靠评测后，再研究：

- 自动团队组建；
    
- 动态模型和工具选择；
    
- 自动任务图重构；
    
- 候选架构搜索；
    
- 自生成工具；
    
- 自动优化提示；
    
- Harness 自修改；
    
- Agent 信用分配。
    

所有自进化修改必须：

1. 在隔离环境生成；
    
2. 通过固定回归集；
    
3. 与当前 Harness 进行成本约束 A/B；
    
4. 检查权限和安全策略变化；
    
5. 由人类批准；
    
6. 支持立即回滚。

# 十一、实践验证与研究性建议的边界

## 已有较强实践验证

- Supervisor–Worker 层级拓扑；
    
- 专业只读子 Agent；
    
- 显式任务状态和依赖；
    
- worktree、分支或容器隔离；
    
- 默认拒绝网络；
    
- 最小权限工具调用；
    
- 确定性测试和安全门禁；
    
- 事件日志和检查点；
    
- 选择性委派；
    
- 紧耦合任务限制并行；
    
- 单一集成者串行合并。
    

## 有公开机制，但效果证据仍有限

- 大规模 Agent 工作流；
    
- 自动权限 reviewer；
    
- 长时间云端 Agent；
    
- 多候选自动评选；
    
- 数十个以上 Agent 的有效协作；
    
- 自动冲突解决；
    
- 自动语义合并。
    

## 当前仍属于研究方向

- 通用动态团队组建；
    
- 学习型自适应调度；
    
- 跨 Agent 可信长期记忆；
    
- Agent 间信用分配；
    
- 自动搜索团队拓扑；
    
- Harness 运行时自修改；
    
- 大规模去中心化 Coding Swarm；
    
- 无人类参与的高风险审批；
    
- 对数日级真实软件工程任务的标准化评测。

# 十二、最终决策框架

实践中可以使用以下决策顺序：

### 第一问：单 Agent 能否在合理预算内完成？

能，则使用单 Agent。

### 第二问：问题是搜索瓶颈还是写入瓶颈？

搜索瓶颈，增加只读专业 Agent。

### 第三问：写入范围是否可以明确隔离？

可以，则使用独立 worktree 并行；不可以，则保持单写者。

### 第四问：任务是否有显式依赖和长时间恢复需求？

有，则引入 DAG、任务账本和检查点。

### 第五问：候选方案是否能被可靠验证？

能，则可以使用有限 best-of-N；不能，则不要通过 Agent 投票决定。

### 第六问：任务是否重复且流程稳定？

是，则固化为 Workflow-as-Code。

### 第七问：操作是否影响生产、权限、资金或数据？

是，则必须保留人类审批。

# 十三、最终推荐方案

适用于实际 Coding Agent Harness 的最佳默认方案是：

> **一个中心调度器，一套持久任务账本，少量专业只读 Agent，有限数量的隔离写入 Agent，一个统一合并器，一组确定性质量门禁，以及按风险分级的人类审批。**

其默认运行策略为：

1. 单 Agent 开始；
    
2. 先并行侦察；
    
3. 再决定是否拆分；
    
4. 读取可以共享快照；
    
5. 写入必须独立 worktree；
    
6. 每个任务只有一个代码所有者；
    
7. Agent 通过工件交接；
    
8. 调度状态不存放在聊天中；
    
9. 合并由单一集成者完成；
    
10. 测试决定成功；
    
11. 高风险操作由人类批准；
    
12. 只有经过验证的数据才能驱动团队扩展和 Harness 自进化。
    

最终应优化的不是 Agent 数量，而是：

> **单位被接受软件变更的质量、成本、关键路径时间、人工负担和风险。**

这也是区分成熟 Coding Agent Harness 与普通聊天式多 Agent 系统的根本标准。
